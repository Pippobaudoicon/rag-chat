## 0.12.29

- **Mobile accessibility sweep.** Four WCAG fixes in the UI layer; no API, retrieval, or data-model change.
  - *Pinch-zoom restored* (`src/app/layout.tsx`). The viewport dropped `maximumScale: 1` / `userScalable: false`, which failed WCAG 1.4.4 (Resize Text, AA) — Android Chrome honors the lock, so anyone who needed to zoom could not. Unlocking zoom exposed a coupled bug: the composer's `text-[15px]` was overriding the codebase-wide `text-base md:text-sm` input convention (`ui/textarea.tsx`, reached via `PromptInputTextarea` → `InputGroupTextarea` → `Textarea`) down to 15px on mobile, and iOS Safari zooms the viewport when focusing any input under 16px. The lock had been masking it. The composer is now `text-base md:text-[15px]` — 16px on mobile, the intended 15px on desktop. It was the only override; the feedback, search, and sidebar-rename inputs already inherit the safe default.
  - *Screen readers announce the right language* (`src/components/chat/language-context.tsx`). `<html lang>` was hardcoded to `it` while the UI ships six languages, failing WCAG 3.1.1 (Language of Page, A) — VoiceOver/TalkBack read English, Spanish, and German answers with an Italian voice. `LanguageProvider` now syncs `document.documentElement.lang` from the stored preference through a new `UI_LANGUAGE_BCP47` map. The root layout keeps `lang="it"` as the SSR seed, matching the provider's default state.
  - *Orientation unlocked* (`src/app/manifest.ts`). Dropped `orientation: "portrait-primary"`, which failed WCAG 1.3.4 (Orientation, AA) for devices fixed in landscape on a mount.
  - *No keyboard on load* (`src/components/chat/ChatInterface.tsx`). The composer's unconditional `autoFocus` opened the on-screen keyboard on every mobile load, burying the conversation before it could be read. Focus is now driven by a mount effect gated on `(pointer: fine)` through a ref on `PromptInputTextarea`. Deliberately **not** a conditional `autoFocus` prop: React serializes `autoFocus` into SSR HTML (`renderToStaticMarkup` emits `autofocus=""`), so a client-only condition renders the attribute on the client but not the server — desyncing hydration and leaving desktop autofocus dependent on whether React re-fires focus during hydrate. The effect sidesteps both.

Client failures have bounded recovery, a failed pre-create restores the draft, multi-turn pending state stays visible, and the composer uses a non-interactive progress indicator instead of a false local Stop. Generation remains bounded by the 180-second route limit and is not a durable background job: a server crash or deployment can still interrupt it. Added the pure `test:chat-lifecycle` regression suite.

## 0.12.20

- **Answer-language detection: dominance fallback for clear multi-word prompts.** `detectPromptLanguage()` returned `und` for genuine but proper-noun/number-heavy prompts that tinyld scores below 0.9 — e.g. "can you help me understand better John 3?" (en@0.15) — which let an earlier Italian turn's history drive the model to answer in the wrong language. It now accepts the top language below 0.9 when a **conservative dominance fallback** holds: a calibrated **minimum top confidence** (`>= 0.08`) **and** ≥ 4 words **and** an insignificant 2nd-ranked language (`< 0.15`). The min-confidence floor is essential — word count + low secondary alone would also accept a string of foreign-looking proper names that tinyld classifies near-randomly with no rival (e.g. "Gideon Teancum Pahoran Moroni Lehi" → Latin@0.039); the floor keeps those `und` while preserving genuine prompts dragged down by proper nouns + numbers (en@0.145, German@0.100). This keeps all known holes closed — short greetings (≤ 3 words), mixed-language instructions ("Rispondi in italiano: <English>" → en@0.73 but 2nd it@0.27), and weak proper-name classifications all return `und`. The 0.9 high-confidence path is unchanged. Answer-language and retrieval-query translation remain independent (this only affects the answer-language hint + scripture-language preference). New `test:language-policy` regressions: English/German/Italian scripture questions, greetings, short references, mixed-language instructions, and proper-name negatives (Latin/Indonesian @0.039–0.073).

## 0.12.17

- **Tool-specific language routing — Phase C (lazy per-tool translation + prompt-preferred scripture language).** Third step of `docs/TOOL_SPECIFIC_LANGUAGE_ROUTING_PLAN.md`. Translation now happens inside the English-corpus tools, only when a cross-language query is actually retrieved.
  - **`semantic_search` translates lazily.** It accepts the query in the model's natural language and resolves it to the corpus language inside `execute()` via the request-scoped `createRetrievalQueryResolver()` (created in the route, passed into the tools). The resolved English query drives the cache key, embeddings, Pinecone, rerank, and returned `query` metadata, so English semantic retrieval (local same-language fast path → no LLM call) is byte-identical to before; a cross-language query translates once and is memoized across repeats.
  - **`search_conference_talks` translates the searchable text only.** Free-text query + optional title are resolved to the corpus language before inference/matching; speaker and year are structured constraints and pass through untranslated.   - **`lookup_scripture_passage` prefers the prompt's scripture language and never translates.** The tool now takes a `scriptureLanguage` (derived in the route from `detectPromptLanguage().scriptureLanguage`, falling back to the corpus language) independent of the semantic index language — fixing the contract mismatch where Italian scripture requests preferred English. References are matched by language-invariant slugs (no translation); the retriever queries the preferred language first and falls back to the other indexed language only if the passage is absent; the cache is keyed by reference + preferred language. That write keyed on the original question and, now that the tool keys on the *translated* query, would have left two divergent entries; the `answer` field was never read anyway.   - **Tool-local routing telemetry.** `RetrievalToolEvent` / `ChatProgressData` gain optional `routingMs` / `translated` / `inputLanguageCode` / `retrievalLanguage` / `routingModel` / `routingFallbackUsed`, emitted by the translating tools and folded into the persisted retrieval trace (absent for `lookup_scripture_passage`). The global `RetrievalTrace.searchQuery` is gone (translation is per-tool).
  - **Unchanged:** `citation_verifier` (no routing), `/api/search` (still global translation via `CHAT_MODEL` — its migration to `RAG_ROUTING_MODEL` + scripture-language preference is the Phase D follow-up, contract preserved), all gates, citations, source ordering, and payload shapes. `typecheck` + `test:routing` (9/9) + `test:eager` (30/30) + `test:language-policy` (42 checks) clean. ## 0.12.16

- **Phase B correction: confidence-gate `detectPromptLanguage()`.** The local detector previously trusted `tinyld`'s top guess unconditionally, which produced **wrong** explicit answer-language instructions on short input — "Hello" → Italian (0.20), "Grazie" → Polish (0.17), "Ciao, come stai?" → Italian (0.09). It now asserts a concrete language only when `accuracy >= 0.9` and returns `und` otherwise (no name, no `scriptureLanguage`). `tinyld`'s accuracy is sharply bimodal on prompt-length text — confident single-language prompts score ~1.0 while greetings, wrong guesses, and **mixed-language instructions** ("Rispondi in italiano: <English>" → en@0.76) all sit ≤ ~0.76 — so 0.9 cleanly keeps only the confident cluster. `und` is safe: the generation model naturally matches the original prompt. Confident prompts (e.g. Italian `Giovanni 3:16` → `ita` scripture, English `What is faith?` → `en`) are unaffected; English `John 3:16` → `und` → English scripture fallback at the tool. New regression table in `test:language-policy` covers greetings, mixed-language instructions, and Italian/English scripture references.

## 0.12.11

- **Short-circuit the language-routing LLM call for same-language prompts (Phase 2 · P0-A).** `routeQueryLanguage()` previously ran a full `generateText` (structured output, up to 600 tokens) on **every** turn — the `routing` latency phase — even when the prompt was already in the index language (default index = English), where the "translation" is identity. It now detects the prompt language **locally** first (via `tinyld`, a small profile-based detector) and, when the detected language matches the index language, returns the same `QueryLanguageRouting` result without calling the LLM (`searchQuery` = original, `translated: false`, `inputLanguageCode` = the detected 2-letter code). The `routing` phase drops to ~0 on the English path; `preStreamMs` / `serverFirstTextMs` fall correspondingly. Benefits both `POST /api/chat` and `GET /api/search`.
  - **Cross-language & mixed-language fidelity preserved.** The fast-path fires **only** when the prompt is *confidently, dominantly* in the index language — extracted into the pure `detectIndexLanguageMatch()` helper, which requires the top detected language to be the index language with accuracy ≥ 0.9 **and** no significant secondary language (≥ 0.15). Genuinely cross-language prompts (Italian → English index) and **mixed/quoted-language** prompts keep the LLM path. This closes a codex finding: `Rispondi in italiano: <English question>` (or a non-English question quoting a long English passage) is dominantly English by token count, so a naïve top-classification short-circuit would have wrongly answered in English with an untranslated query; the dominance gate routes those through the LLM (calibration: pure prompts classify at accuracy 1.0, any mixing drops to ≤ ~0.83). tinyld also returns nothing for too-short/ambiguous input (e.g. a bare `Alma 32:21`) → LLM fallback.
  - **Library choice — tinyld over franc (justification):** on realistic LDS prompts `franc` misclassifies common English (e.g. "What is the law of chastity…" → `sco` Scots), so a `=== eng` gate would under-fire and forfeit the win on most English queries. `tinyld` classifies en/it/es/fr correctly with high confidence and returns empty for too-short input. tinyld emits ISO 639-1; the index `CorpusLanguage` (`eng`/`ita`) is mapped to `en`/`it` for the comparison.
  - **Contract unchanged:** the `QueryLanguageRouting` shape is byte-identical; `translated` has no external consumers (it is now `false` on the same-language path, which is also more accurate). Redis-cached routing (the plan's optional step 4) was intentionally **not** added — kept minimal.
  - **Tests/guards:** new `npm run test:routing` (`scripts/test/language-routing.test.ts`) — a pure, network-free regression test asserting pure-language prompts short-circuit while mixed/quoted/cross-language prompts use the LLM (9 cases incl. the codex repro). `npm run eval` — recall/MRR unchanged and the `italian-*` cross-language cases still pass (they detect as `it` and keep the LLM translation path, so they are unaffected by construction).

## 0.12.10

- **Parallelize the chat pre-stream preamble (Phase 2 · P0-B).** `POST /api/chat` previously awaited a chain of mostly-independent preamble operations serially: conversation load → messages load → language routing → memory brief → user prefs, each in its own latency phase. The independent reads (messages load, language routing, memory brief, user prefs) now run concurrently in a single `Promise.all`, collapsing `preStreamMs` from roughly the **sum** of those phases toward their **max**. Individual `phases.*` durations are unchanged; only their overlap improved. No behavior change otherwise.
  - **Gate ordering preserved.** The `auth` (401), `ratelimit` (429), and conversation **ownership** (404) gates all resolve *before* the parallel batch, so a rejected request never speculatively pays for the language-routing LLM call or the memory/prefs reads — and a deleted/unowned `conversationId` still 404s promptly rather than waiting on (or being masked by a failure in) routing/memory/prefs (codex review). The ownership gate is a single indexed `convLoad`; the heavier `messagesLoad` runs inside the batch behind it. `entitlements` + `ratelimit` likewise stay sequential ahead of the batch to honor "don't burn LLM cost on a request you're about to reject" — the routing LLM call dominates the batch anyway, so the reads hide behind it.
  - **Routing for the deferred-question case.** Routing runs inside the batch for the common case (question known up front). For regenerate requests whose transport omits the question text (resolved from stored history), the single routing call is deferred until after the conversation loads and the fallback question is known — still exactly one `routeQueryLanguage` call per turn.
  - **Early returns and write-ordering intact:** 401 (auth), 429 (ratelimit), 404 (conversation not found / not owned), and 400 (empty question) all still fire, and no writes (user-message insert, conversation create, per-conversation style override) happen before validation/ownership passes. `prefs` is now fetched eagerly in the batch instead of lazily, so the `prefs` phase is recorded on every turn (previously only when no per-conversation style override existed).

## 0.9.0

- Added graph-aware reranking over the cross-reference graph already projected into Pinecone metadata. A retrieved chunk that is cross-referenced by several others in the result neighborhood is central to the topic, so it gets a small, capped score boost (a principled tiebreaker among semantically-close candidates, like the topic/entity boost). `semantic_search` reranks the whole result set; `lookup_scripture_passage` keeps the requested passage pinned and reranks only the supporting cross-references/study-helps. Shared helper: `tools/shared/graph-rerank.ts`.
- This is genuinely multi-hop (expanded chunks carry their own `related_ids`, so hop-2 connectivity is observed) and needs no sidecar: the 60MB `cross_references.jsonl` graph is never shipped to the runtime — only the per-vector forward edges already in Pinecone metadata are used. (Full-graph authority signals, e.g. TG-hub co-citation, remain a future offline/scraper-side metadata enhancement.)
- Graph-aware reranking is gated behind the `RAG_GRAPH_RERANK` flag (`src/lib/rag/flags.ts`), **default off**, so it can be A/B-measured before it is trusted unconditionally.
- Added a retrieval eval harness (`npm run eval`, `scripts/eval/`): runs a golden set through the real retrieval pipeline and reports relevance metrics (MRR, recall, structural checks) with graph-rerank off vs on. First run: rerank improves MRR ~0.35 → ~0.44 with 0 cases worsened. The harness also surfaced two pre-existing issues to fix next: Italian scripture chunks leaking into English results, and `parseScriptureSelection` still returning Italian `canonicalBook` values (so `lookup_scripture_passage`'s strict book/chapter filter is dead post-English-migration and falls back to unfiltered semantic results).
